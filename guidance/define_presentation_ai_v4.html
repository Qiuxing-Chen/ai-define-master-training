Slide 02 · 打好基础
先搞懂：Define-XML 是什么
02

它是什么

一份随临床试验数据一起递交的"数据说明书"，用标准 XML 格式写成。它逐一描述：数据里有哪些数据集、每个变量是什么含义、值从哪来、按什么规则取值。

为什么要做它

审评员拿到的是成百上千列数据，光看数据本身看不懂。Define-XML 就像一张"导览地图"：告诉他们每个变量什么意思、怎么算出来的、对应 CRF 的哪一页，让数据可读、可核。

做不好会怎样

它是 CDISC 标准和监管递交的硬性要求。缺失或有错（比如引用断链），递交很可能被退回返工——所以它必须又准又完整。

它本质上是一棵引用密集的树：全靠一套 OID 把节点互相挂住
📖 三个新词先记住：域 / 数据集＝一类数据的表，如 AE（不良事件）、DM（人口学）；变量＝表里的一列；受控术语（CodeList）＝某个变量允许填哪些值的清单。后面反复会用到。
一句话：Define-XML 是让别人"看得懂你数据"的说明书，也是合规递交的入场券。
Slide 03
先看传统方式怎么做
03

路线 A：metadata file + P21

人工整理好元数据表，导入 Pinnacle 21 工具，由工具生成 define.xml 并同步做合规校验。

路线 B：metadata file + SAS

人工整理好元数据表，再用 SAS 程序读取并拼装输出 define.xml。

注意两条路的前半段完全一样：都必须先有一份人工整理好的 metadata file——人工补齐三层规则（研究级 → 共享级 → 域级），差别只在后半段"谁来生成"。

它的优点

  • 规则稳定时效率高，结构清晰、可复查
  • P21 路线自带合规校验，SAS 路线灵活可定制
  • 适合成熟项目反复复用
AI 不是要替代这两条路，而是补足它们前面最费人的那段"整理"。
📖 三个名词：元数据（metadata）＝不是试验数据本身，而是"关于数据的说明"（某变量叫什么、什么类型、取值范围、怎么算的）；metadata file＝人工维护的元数据表，通常是 Excel，逐行写清每个变量；P21（Pinnacle 21）＝行业常用的 CDISC 合规校验与 define 生成工具。
Slide 04
传统方式的痛点在哪
04
这一步极其耗 FTE：要通读 spec、IG、SAP 等多份文件，逐个变量、逐个值级手工填表，还要跨角色反复对齐和返工。成本和风险几乎全集中在这里。

需求碎

  • 规则散落在 spec、CDISC IG、SAP、共识文件等多处
  • 前端整理吃掉大量 FTE
  • 反复对齐，整理成本高

值级复杂

  • 一个变量在不同条件下取值不同，条件多、容易漏
  • 说明容易前后不一致
  • 一旦漏了或错了，就得返工重来

沟通反复

  • 探索性分析的衍生规则容易反复
  • 多角色沟通，理解容易有偏差
  • 来回确认 → 多次返工，拖慢进度
📖 这些名词是啥：FTE＝全职人力当量，衡量一件事要占掉多少人力；Spec＝specification file 标准数据集说明书（定义每个变量长什么样）；CDISC IG＝CDISC 的实施指南（行业标准规则）；SAP＝统计分析计划。规则分散在它们里面，正是"需求碎"的根源。
所以 AI 要解决的，正是这段"需求整理 + 反复修订"的闭环，而不是替换后面成熟的 P21 或 SAS 生成器。

  • 需求更快收敛落地
Slide 06 · 核心机制
AI 制作 Define 的完整流程
06
🧩 底层框架：build_define_v2.ipynb——本次 AI 问询生成 define 的全部流水线都跑在这个 notebook 里。AI 负责读懂它、按三层问询把规则问清、改对 YAML；notebook 负责把 YAML 稳定编译成 define.xml 并自检。

💡 点击任意节点，展开该步的输入 / 动作 / 产出 / 要点。最后一个环节"迭代闭环"会带着自检发现的缺口回到"三层问询"，形成一个可追溯的循环。

两条铁律：source-of-truth 永远是 YAML；改内容就改 YAML，别手改 define.xml——手改会在下次编译时被覆盖。
📖 YAML：一种人也读得懂、机器也能解析的文本配置格式。本方案用它来存放元数据——比 XML 好读好改，是我们真正维护的"源"。
🙋 想一想 & 试一试
中间层为什么用 YAML，不用 JSON？
参考答案：这层要给人看、要人审、还要 AI 反复读写，YAML 更合适：可读性好、能写注释（方便标溯源）、diff 清爽好 review。标准 JSON 不支持注释（JSONC、JSON5 等方言才行，但已不是标准 JSON），更适合机器传输而非人机共同维护。

Slide 09
模块解耦 · 多人协作与审核
09

🧱 独立模块

  • aCRF 页码 acrf.yaml
  • 计算方法 methods.yaml
  • 注释 comments.yaml
  • codelist codelists.yaml
  • 各域文件 datasets/*.yaml

👥 分工协作

  • 按模块分支并行推进
  • 责任到人、互不阻塞
  • codelist / 方法可跨域复用
  • 域文件各自独立维护

🔍 变更可审

  • 每次改动都能 diff 对比
  • PR 审核、留痕可追溯
  • 升版一处改、处处生效
  • 知识沉淀不散落在个人手里
📖 Git / diff / PR：Git 是版本管理工具，diff 能逐行看出改了什么，PR（合并请求）让改动在合入前先由他人复核。三者合起来，让改动"看得见、可审核、可回溯"。
各模块进 Git，按模块分支并行、逐条 diff 审核——责任到人，变更可追溯。

Slide 13 · Hands-on
实操练习：自己跑通一次完整闭环
13

① 配好路径

  • 把项目复制到自己的 folder
  • 打开 config.yaml
  • 核对 sdtm_dir（xpt / acrf.pdf 目录）
  • 核对 dept_dir / study_dir
  • 确认 study_files 里 spec / codelist / aCRF 文件名对得上

② 跑出 define.xml

  • 打开 build_define_v2.ipynb
  • 选好 Python 环境（kernel）
  • Run All，按 6 步流水线执行
  • 约 20 秒生成 define.xml
  • 浏览器打开 define.xml 看渲染效果

③ AI 问询改一处

  • 选一个想改的点：method / comment / codelist
  • 问 AI：这个内容在哪个 yaml？
  • 让 AI 定位并修改对应 datasets/*.yaml 或共享级 yaml
  • 重新 Run 编译
  • 对比 diff 确认只改了目标处

🎯 试试这些改动

  • 把某个变量的 Label / Comment 改一句更清楚的说明
  • 给某个 method 补一段计算逻辑描述
  • 调整某个 codelist 的取值或解码文本
  • 改完记得：改 YAML，别手改 define.xml

✅ 完成标准

  • define.xml 成功生成、能正常打开
  • 自检无新增断链 / OID 冲突
  • 目标内容按预期改动，其余不受影响
  • 能说清：这次改的"源"是哪个 yaml
卡住很正常——先回到问题："我要改的这条，源在哪个 yaml？"定位对了，剩下就是改一处、重编译、看 diff。
